# 多言語対応 (i18n) 仕様

- 対応言語: **日本語 (ja) / 英語 (en)**、UIから随時切替可能
- 文書バージョン: 0.1 / 2026-11-15
- 関連: `SPEC.md` §1.6, §3.2, §4.1〜4.3, §5.3

---

## 1. 方針

- 日本語・英語の2言語を同梱し、**アプリ内のどこからでも即時に切り替えられる**。リロードを要求しない。
- 翻訳は静的バンドルに同梱する（ネットワーク取得しない）。PWAのオフライン動作を壊さないため。
- 言語切替はヘッダの切替ボタン（`日本語 / English`）と設定画面(S6)の両方から可能。

---

## 2. 最重要原則: 言語 ≠ 判定基準

**表示言語の切替は、トリアージ判定基準（`RuleProfile`）を一切変更しない。**

これは本アプリで最も誤りやすい箇所である。START法の基準値は国・組織により異なり、特に呼吸数で差がある。

| プロファイル | 呼吸数で赤とする条件 | 循環の指標 |
|---|---|---|
| `JP-FDMA`（日本・消防庁標準／**v1で採用**） | **≦ 9 または ≧ 30** 回/分 | CRT ≧ 2秒 または 橈骨動脈触知不能 |
| `US-START`（米国原典／v1未実装） | **> 30** 回/分 のみ | CRT > 2秒 または 橈骨動脈触知不能 |

英語UIに切り替えたユーザーが「米国版STARTの基準で採点されている」と誤解すると、**誤った基準を習得してしまう**。
これは教育アプリとして最も避けるべき事故である。したがって:

1. `locale` と `profile` は**完全に独立した状態**として保持する。一方が他方を変更してはならない。
2. **英語UIでも採用基準が `JP-FDMA` であることを明示する。**
   リファレンス画面(S5)と免責表示に、以下に相当する英文を常時表示する。

   > This trainer uses the START criteria standardized by the Japan Fire and Disaster Management Agency
   > (respiratory rate **≤9 or ≥30** /min indicates Immediate). These thresholds differ from the original
   > US START protocol (respiratory rate **>30** /min). This app is for training only — in a real incident,
   > follow the protocol of your own organization.

3. 将来 `US-START` プロファイルを実装する場合も、**言語切替とは別の明示的な設定項目**として提供する。
   言語選択に連動させてはならない。

## 3. 実装方式

### 採用: 自前の軽量i18n（約50行）+ `Intl`

```ts
// src/i18n/types.ts
export type Locale = 'ja' | 'en';
export type TranslationKey = keyof typeof ja;          // ja を正とした型
export type Messages = Record<TranslationKey, string>; // en は同一キー集合を強制

// src/i18n/index.tsx
const LocaleContext = createContext<{ locale: Locale; setLocale(l: Locale): void; t: T }>(...);
export function useI18n(): { locale: Locale; setLocale(l: Locale): void; t: T };

// t はキーを型で縛り、プレースホルダを置換する
// t('judge.rrHigh', { rr: 32 })  →  "呼吸数 32回/分（30回以上）"
```

### i18next / react-i18next を採用しない理由
1. **バンドルサイズ。** i18next + react-i18next で約40KB(min+gzip)。
   初回ロード300KB未満の目標(SPEC §4.5)に対し、文字列数が数百・言語2つの本件では割に合わない。
2. **型安全性。** 自前実装なら `ja.ts` のキーを正として `TranslationKey` 型を導出でき、
   存在しないキーや未翻訳がコンパイルエラーになる。i18next は既定でこれを提供しない。
3. **複数形・性・格変化の要件がない。** ja/en の2言語で、必要な変化は数値の埋め込みのみ。
4. ネットワークからの翻訳ロードやバックエンド連携も不要（バックエンドが存在しない）。

数値・時間の整形は `Intl.NumberFormat` / 自前の `formatDuration` を使う。
タイムは `1分23.45秒` / `1:23.45` のようにロケールで表記を変える。

## 4. 言語の決定とURL

### 初期言語の決定順序
1. localStorage の `settings.locale`（過去に明示選択していればそれを最優先）
2. URLクエリ `?lang=ja` / `?lang=en`
3. `navigator.language` が `ja` で始まれば `ja`
4. 上記いずれでもなければ `en`

### URLクエリを受け付ける理由
Xへ投稿されたURLを開いた人に、**投稿者と同じ言語**で表示させるため（§7）。
`?lang=` は初期値の決定にのみ使い、アプリ内で切り替えた後はURLを書き換えない（履歴を汚さない）。

### 切替時の副作用
- `document.documentElement.lang` を `ja` / `en` に更新する。
  スクリーンリーダーの読み上げ言語が切り替わるため、a11y上必須(SPEC §5.3)。
- localStorage の `settings.locale` に保存する。
- 出題中の症例は破棄しない。**10問連続モードの途中でもタイマーを止めずに切り替えられる**
  （言語切替で有利・不利が生じないよう、再レンダリングのみで状態は保持する）。

## 5. ドメイン層への影響（設計変更）

`src/domain/` は **React非依存・副作用なし**であり、**表示文字列を一切持たない**。
この原則を守るため、SPEC §4.3 の型を以下に変更する。

### 変更前
```ts
export interface Judgement {
  category: Category;
  decidingStep: DecidingStep;
  rationale: string[];        // ← 日本語文字列が混入してしまう
}
```

### 変更後
```ts
export interface RationaleItem {
  key: string;                                   // 翻訳キー（例 'rationale.rrHigh'）
  params?: Record<string, string | number>;      // 例 { rr: 32, threshold: 30 }
}

export interface Judgement {
  category: Category;
  decidingStep: DecidingStep;
  rationale: RationaleItem[];
}
```

- `domain/explain.ts` は**翻訳済みの文章ではなく `RationaleItem[]` を組み立てる**。
  文章化は表示層（`features/learn/`）が `t()` で行う。
- 同様に、傷病者イラストの状況テキストも文字列ではなくキーで保持する。

```ts
export interface TriageCase {
  patient: {
    illustrationId: string;
    situationKey: string;      // 例 'situation.walkedOnOwn' → ja/en 両方に翻訳を持つ
  };
  // ... 以下 SPEC §4.3 と同じ
}
```

この変更により、ドメイン層のテストは言語に依存せず、翻訳の追加でロジックのテストが壊れない。

## 7. Xポスト / OGP の扱い

### 投稿文（言語別）
```
ja: START法トリアージ 10問チャレンジ 全問正解！
    タイム 1分23.45秒
    #STARTトリアージ #災害医療 #トリアージ訓練

en: Perfect score on the START triage drill — 10/10
    Time 1:23.45
    #STARTtriage #DisasterMedicine #MassCasualty
```
- 投稿時の `locale` に応じてテンプレートとハッシュタグを選択する。
- **投稿URLには `?lang=<locale>` を付与する。** 投稿を見た人が投稿者と同じ言語で開けるようにする。
  例: `https://start.keiku-labo.space/?lang=en`

### OGP
静的HTMLは1種類しか配信しないため（バックエンドなし）、OGPは次の方針とする。
- `og:title` / `og:description` は**日英併記**（`og:description` に2行で入れる）
- `og:locale` = `ja_JP`、`og:locale:alternate` = `en_US`
- `<html lang>` の初期値は `ja`（JSが起動後に切り替える）
- `og:image` のOGP画像内テキストも日英併記で1枚にまとめる（画像を2種持たない）

## 8. 対訳表（用語統一のため、実装時はこの表に従う）

### トリアージ区分
| コード | 日本語 | English | 色 |
|---|---|---|---|
| `I` | I類・緊急治療群 | **Immediate** | 赤 / Red |
| `II` | II類・非緊急治療群 | **Delayed** | 黄 / Yellow |
| `III` | III類・軽処置群 | **Minor** | 緑 / Green |
| `0` | 0類・死亡群 | **Deceased** | 黒 / Black |

- 回答ボタンは短いラベルを使う: `Immediate` / `Delayed` / `Minor` / `Deceased`。
- 英語UIでもローマ数字 `I / II / III / 0` を併記する（日本の区分体系であることを示すため、
  かつ色のみに依存しない3重符号化を維持するため。SPEC §5.3）。
- `Deceased` は日本の「死亡群」に対応する訳。英語圏では `Expectant` が使われる場合もあるため、
  リファレンス画面(S5)でのみ `Deceased (also called "Expectant")` と補記する。

## 9. テストで担保すること

1. **キー集合の一致**: `Object.keys(ja)` と `Object.keys(en)` が完全一致すること（未翻訳・余剰キーの検出）。
2. **プレースホルダの一致**: 各キーで `{name}` 形式のプレースホルダ集合が ja/en で一致すること
   （例: ja に `{rr}` があるのに en にない、という事故を防ぐ）。
3. **空文字の禁止**: いずれのロケールにも空文字の値が存在しないこと。
4. **ドメイン層の言語非依存性**: `judge()` / `generateCase()` のテストが `locale` に一切依存しないこと
   （`domain/` 配下から `i18n/` への import が存在しないことを静的に検査）。
5. **`RationaleItem.key` の実在性**: `explain.ts` が生成し得る全キーが ja/en 双方に存在すること。
   全 `DecidingStep` × 各分岐を網羅して検証する。

## 11. 非スコープ

- 日本語・英語以外の言語（キー構造は追加に耐えるが、v1では同梱しない）
- 右横書き(RTL)対応
- 言語ごとに異なる `RuleProfile` の自動適用（§2 の通り、意図的に行わない）
- サーバサイドレンダリングによる言語別OGP配信（バックエンドを持たない方針のため）

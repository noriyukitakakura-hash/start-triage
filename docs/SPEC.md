## 1. 企画

### 1.1 背景と課題
災害現場・多数傷病者事案における一次トリアージ（START法）は、
**「判定の順序」と「境界値の即断」** が成否を分ける。しかし実際の訓練機会は年数回に限られ、
紙のフローチャートを「読んで理解する」ことと「30秒以内に判定し続けられる」ことの間には大きな差がある。

### 1.2 プロダクト概要
ブラウザで動く、START法の反復トレーニングアプリ。
1症例ごとに「傷病者のイラスト（歩行可否の手がかり）」と「ランダム生成されたバイタル」を提示し、
利用者が4つのトリアージ区分から選択する。学習モードで理屈を固め、10問連続モードで速度と正確性を測る。

### 1.3 ターゲット
- 消防職員・救急隊員（救命士含む）
- DMAT隊員、災害拠点病院の医師・看護師
- 看護学生・医学生・救急救命士養成課程
- 事業所/自治体の防災訓練参加者（一般向け導入）

### 1.4 提供価値 / 差別化
| 観点 | 本アプリ |
|---|---|
| 判定の体得 | 境界値（呼吸9/10回、29/30回、脈拍120、CRT 2秒）を意図的に高頻度出題し、迷いを潰す |
| 速度の可視化 | 10問連続の経過時間を計測。自己ベストを更新する動機づけ |
| 外部発信 | 10問全問正解時のみ、Xへタイムを投稿可能（達成の希少性＝投稿価値） |
| 導入障壁 | インストール不要・ログイン不要・完全無料・オフライン動作 |

### 1.5 KPI（初期）
- 1セッションあたりの平均出題数 ≥ 20問
- 10問連続モードの全問正解率（初回 vs 5回目以降）の改善
- Xポスト実行数 / 全問正解数

### 1.6 スコープ外（v1）
- ログイン、サーバー保存、全国ランキング（※時間はクライアント計測のため検証不能。1.7参照）
- 二次トリアージ（PAT法）、小児用START（JumpSTART）
- マルチプレイ（3言語目以降の多言語化も非スコープ。ja/en は対応する → `docs/I18N.md`）

### 1.7 医療・倫理・法務上の注意（必須記載事項）
- 免責文: **「本アプリは教育・訓練目的のシミュレーションです。実際の傷病者対応は所属機関のプロトコル・指示に従ってください。」**
- **提示方法: 初回起動時にダイアログで明示的な確認（ボタン押下）を求める。**
  画面の片隅に小さく常時表示するより確実に読まれ、医療教育アプリとして妥当な形である。
  確認した版番号を保存し、免責文を実質的に改訂したら再度確認を求める（`DISCLAIMER_VERSION`）。
  設定シートからいつでも再読でき、到達性は失われない。
  出題画面に常時表示しないのは、判定材料をスクロールなしで収めるため（§5.1）。
- START法の基準値は地域・組織のプロトコルにより差異がある。採用基準を明示し、プロファイル切替可能な設計とする（§3.2）。
- 傷病者イラストは**実写を使用しない**。実在人物の負傷画像は権利・倫理・心理的配慮の観点で不適。自前のベクターイラストで表現する。
- 経過時間はクライアント計測であり改ざん可能。**SNSへの自己申告共有に限定し、競争ランキングは実装しない**（将来実装する場合はサーバー側での出題・計測検証が前提）。

## 2. 機能仕様

### 2.1 画面一覧
| ID | 画面 | 概要 |
|---|---|---|
| S1 | ホーム | モード選択、自己ベストタイム、学習統計サマリ、リファレンスへの導線 |
| S2 | 学習モード | 1症例ずつ出題 → 回答 → 即時フィードバック＋解説 → 次へ（無制限） |
| S3 | 10問連続モード | 経過タイマー表示、進捗(n/10)、フィードバックなしで連続出題 |
| S4 | 結果 | 10問の正誤一覧、タイム、全問正解時のみXポストボタン、再挑戦 |
| S5 | リファレンス | START法フローチャート、4区分の定義、採用基準値の明示 |
| S6 | 設定 | ルールプロファイル、境界値出題頻度、サドンデス有無、タイマー表示、統計リセット |

### 2.2 症例の提示内容（1症例カード）
```
┌─────────────────────────────┐
│  [傷病者イラスト]                  │  ← 歩行可否の手がかり
│  「呼びかけに応じて自力で歩いてきた」      │  ← 状況テキスト1行（曖昧性排除）
├─────────────────────────────┤
│ 呼吸      32 回/分                 │
│ 橈骨動脈   触知可                   │
│ 脈拍      110 回/分                │
│ CRT       1 秒未満                  │
│ 指示応答   従える                   │  ← 実測モードでは出さない（声をかけて確かめる）
└─────────────────────────────┘
│ [ I 赤 ] [ II 黄 ] [ III 緑 ] [ 0 黒 ] │
```
- **歩行可否は画像で判断**。ただし「立っている＝歩行可能」とは限らないため、画像に加えて
  状況テキスト1行を必ず添え、判断の曖昧性を排除する（例: 立位イラスト＋「立っているが足が動かず歩けない」）。
- **呼吸数の提示方式は2つある**（設定で切替。**既定は実測モード**）。詳細は `docs/OBSERVATION.md`。

| 方式 | 呼吸数の提示 | 訓練する技能 |
|---|---|---|
| `observed`（実測・**既定**） | 胸郭を数え、爪床を圧迫し、脈に触れて自分で測る | 現場の実務 |
| `numeric` | すべて数値で提示する | 閾値の正確な記憶（呼吸数 9/10・29/30、CRT 2.0秒） |

> 設定は `vitalsPresentation` 一つで呼吸数・CRT・脈拍のすべてに効く。
> 「現場を再現するか否か」という一つの軸であり、項目ごとに切り替えない。
>
> **計測器は常時表示する。** 呼吸・CRT・脈拍を横3列に並べる。
> 爪床の色も脈の拍動も、傷病者を前にすれば常に目に入る情報であり、
> 開かないと見えないのは現場の再現として不自然であるため。
>
> 3つのセルは同じ骨格（ラベル・図・読み取り・操作）で高さを揃える。
> 揃っていないと視線が落ち着かず、どれが未測定なのかも読み取りにくい。
> **数値モードも同じ枠を使い**、計測器の代わりに数値を入れる。
> モードを切り替えても視線の置き場所が変わらない。
>
> **CRT の残り秒数は圧迫中だけセルの外（上）に出す。** 読み取り欄は図のすぐ下にあり、
> スマートフォンで爪を押すと押している指に覆われて読めない（`docs/OBSERVATION.md` §3.4）。
>
> CRT の押下対象は**図の領域全体**とする。爪そのものを対象にすると 28px 程度となり
> タッチ目標として小さすぎる。押下対象は一つに限り、操作欄には押し方の説明だけを置く。
> 同じ名前の操作が二つ並ぶと、どちらを押すのか迷わせるため。
>
> **実測モードでは境界値症例が出題されない**（`docs/OBSERVATION.md`）。
> 呼吸数と CRT の双方にマージンが入り、どのステップも閾値ちょうどの値を取れなくなるため。

> **既定を実測にする理由。** 現場で必要なのは「見て判断する」技能であり、
> 数値を読む練習は目的を絞った補助である。既定で実測にすることで、
> 何も設定しない利用者が現場寄りの技能を訓練できる。
>
> 副作用として、**既定では呼吸数の境界値（9/10・29/30）が出題されない**
> （実測モードは閾値から4以上離す制約があるため。`docs/OBSERVATION.md` §2）。
> 閾値そのものを覚えたい場合は設定で数値モードに切り替える。

- **数値モード**: 自発呼吸なしの症例のみ、回答前に `気道確保を行う` ボタンを1回挟む。
  押すと「気道確保後も自発呼吸なし」/「気道確保により呼吸再開（RR 14回/分）」が開示される。
  → これがないと I類（赤）と 0類（黒）の区別がテキスト読解になり、手技の順序が学習できない。
- **実測モード**: `気道確保を行う` を**全症例に表示する。**
  呼吸数の数値が出ないため、ボタンの有無が観察前に無呼吸であることを漏らしてしまう。
  自発呼吸がある症例で押した場合は「自発呼吸を確認。気道確保は不要」と返し、判定は変えない。
  実際のSTART法の手順（呼吸を確認し、なければ気道確保）にも忠実になる。
- 回答ボタンは **色・ローマ数字・和文ラベルの3重符号化**（色覚多様性への配慮、§5.3）。

#### 声かけと反応（意識の実測）

実測モードでは**指示応答の値も出さない**。傷病者に声をかけ、返ってきた反応から
従命の可否を判断する。呼吸数・CRT・脈拍と同じ扱いである。

| 声かけ | 従命を確認できるか |
|---|---|
| 聞こえますか？（呼名） | **できない。** 反応の有無しか分からない |
| 目を開けてください | できる |
| 手を握ってください | できる |

> **この機能の教育上の核心は「反応がある」と「指示に従える」は違うという点にある。**
> うめき声を上げる、手を払いのける——これらは反応だが従命ではなく、
> START法ではいずれも I類（赤）である。値を読むだけでは決して訓練できない区別である。
>
> 選択肢に呼名を混ぜてあるのは、**どう声をかけるか自体が判断の一部**だからである。
> 呼名にしか応じていない状態で回答した場合は、解説でその旨を指摘する。

- **押すまで反応を出さない。** 先に見せては、確かめる行為そのものが訓練にならない。
- **同じ声かけを繰り返しても反応は変わらない。** 症例の性質であるため。
- **声かけは回答の前提条件ではない。** 確かめずに答える自由を残す（誤れば解説で分かる）。
- ボタンと吹き出しは**イラストに重ねる**。イラストには余白があるため高さが増えず、
  呼吸の計数を犠牲にしない。ただし**重ねる範囲はイラストだけに限る**。
  `.case-figure` 全体に重ねると状況説明文をボタンが覆ってしまう。
- 吹き出しは図の上端中央に出す。全13種のうち立位でも臥位でも、
  **胸郭より上の空白に収まる**位置であり、呼吸の観察を妨げない。
- 支援技術には実測モードでも真の値を渡す（`sr-only`、§5.3）。
- 数値モードでは声かけを出さず、従来どおり `指示応答 従える` を表示する。

### 2.3 学習モード (S2)
- 回答後に即時フィードバック: 正誤、正解区分、**判定が確定したステップのフローチャート上ハイライト**、解説文。
  - 解説文は生成した症例データから自動組み立て（例: 「歩行不能、呼吸数32回/分（30回以上）→ この時点で I類（赤）が確定。以降の評価は不要です。」）
- **解説はボトムシートで出す。** ページ本体を動かさず、背後に症例が見え続ける。
  解説が長い場合もシート内部だけがスクロールする。ネイティブの `<dialog>` + `showModal()` を使い、
  フォーカストラップ・Esc・`::backdrop` を標準機能で得る。
  Esc や背景タップで閉じたら、回答バーから `解説を見る` で再表示できる。
- 実測モードでは**計数精度と区分判定を分離して**提示する。
  例: 「推定 34回/分 ／ 実際 36回/分（誤差 −2）→ 数え値はずれましたが、『30回以上』という判断は正しいです。」
- 「次の症例」で即次へ。回数無制限。中断・再開自由。
- セッション統計（出題数、正答率、区分別の誤答マトリクス）をlocalStorageに累積。

### 2.4 10問連続モード (S3/S4)
- 開始トリガー: ホームの「10問チャレンジ」→ カウントダウン3秒 → 1問目表示と同時にタイマー開始。
- 計測: `performance.now()` 差分。1問目描画完了から10問目回答確定まで。ミリ秒精度。
- **出題中の表示はアナログ時計。** 経過時間なので針は回り続ける。
  数字を読まなくても経過の見当がつく。結果画面は数値表示のまま（記録とXポストに正確な値が要る）。
  `prefers-reduced-motion` では数値へフォールバックし、`sr-only` で数値を常に併記する。
- 出題中はフィードバックを一切出さない（正誤を伏せる）。
- 出題構成（固定比率＋シャッフル）:

| 正解区分 | 問数 |
|---|---|
| I類（赤） | 4 |
| II類（黄） | 2 |
| III類（緑） | 2 |
| 0類（黒） | 1 |
| ランダム | 1 |

  うち **4問以上を境界値症例**とする（下記 §3.3）。

  > **境界値の下限には構造的制約がある。** 境界値を取り得るのは呼吸数・循環・意識の
  > 3ステップのみで、III類（歩行）と0類（気道確保）は真偽値判定のため境界値が存在しない。
  > したがって下限を満たせるのは I類4問 + II類2問 = 6問のみであり、
  > 不足時は **I類・II類側の確定ステップを境界値可能なものへ差し替える**（区分の構成比は維持する）。
  > I類4問すべてが気道確保を引くと上限3問となり下限に届かないため、この差し替えが必須である。
- **1セット内でイラストと状況文を重複させない。** 同じ絵が2回出ると、
  前問の記憶で答えてしまう。生成の後段でイラストと状況文だけを差し替える
  （`judge` は `patient` を見ないので、区分の構成比にも境界値の数にも影響しない）。
- 結果画面: 10問の正誤一覧（各問をタップすると解説シートが開く）、合計タイム、自己ベスト更新表示。
- **自己ベストは全問正解の回だけ記録する。** 誤答を含む速い回が完答より上に来ないようにするため。
- **自己ベストは呼吸数の提示方式ごとに分けて記録する。**
  実測モードは観察時間が支配的になるため、数値モードのタイムと比較できない。
  単一の記録にすると比較不能なタイムを同じ記録として扱ってしまう（`docs/OBSERVATION.md` §3.6）。
- **実測モードで 10/10 の場合のみ** `Xに投稿する` ボタンを表示する。
  それ以外は非表示（文言: 「実測モードで全問正解すると投稿できます」）。
  - 全問正解に限るのは、達成の希少性が投稿の価値になるため
  - **実測モードに限るのは、数値を読むだけの数値モードではタイムが短く、
    かつ現場で必要な「見て判断する」技能を示さないため。**
    共有される記録を現場寄りの技能に揃える
  - 自己ベストの記録自体は両モードで行う（投稿可否とは別の話）
- サドンデス設定（既定OFF）: ONの場合、1問誤答した時点で即結果画面へ。

### 2.5 Xポスト仕様
- 方式: **X Web Intent**（APIキー・OAuth・サーバー不要）
  `https://x.com/intent/post?text=<encoded>&url=<appUrl>&hashtags=<tags>`
  を `window.open(url, '_blank', 'noopener,noreferrer')` で開く。
- 投稿URLには `?lang=<locale>` を付与し、投稿を見た人が投稿者と同じ言語で開けるようにする（I18N.md §7）。
- 投稿文に**呼吸数の提示方式を明記する**。タイムの比較条件が異なるため（`docs/OBSERVATION.md` §3.6）。
- 投稿文テンプレート（編集可能な状態でXの作成画面に渡る。言語別に用意）:
  ```
  START法トリアージ 10問チャレンジ 全問正解！
  タイム 1分23.45秒
  #STARTトリアージ #災害医療 #トリアージ訓練
  ```
- 自己ベスト更新時は1行追加（`自己ベスト更新 🎉`）。
- 投稿ボタン押下をlocalStorageに記録（KPI計測用、送信はしない）。
- OGP: `index.html` に `og:title` / `og:description` / `og:image`（1200×630の静的PNG）を設定し、
  シェア時にカード表示されるようにする。

## 3. トリアージ判定ロジック（コアドメイン）

### 3.1 区分
| コード | 区分 | 色 | 意味 |
|---|---|---|---|
| `I` | I類・緊急治療群 | 赤 | 生命を救うため直ちに処置が必要 |
| `II` | II類・非緊急治療群 | 黄 | 多少の遅れが許容される |
| `III` | III類・軽処置群 | 緑 | 軽傷、歩行可能 |
| `0` | 0類・死亡群 | 黒 | 気道確保後も自発呼吸なし |

### 3.2 判定アルゴリズム（ルールプロファイル `JP-FDMA`、v1で実装）
```
1. 歩行可能か?
   YES → III（緑）  ... 終了
   NO  → 2へ
2. 自発呼吸はあるか?
   NO  → 気道確保
         → 呼吸再開 → I（赤） ... 終了
         → 再開せず → 0（黒） ... 終了
   YES → 3へ
3. 呼吸数 ≦ 9 または ≧ 30 回/分?
   YES → I（赤） ... 終了
   NO  → 4へ
4. 循環: CRT ≧ 2秒 または 橈骨動脈 触知不能?
   YES → I（赤） ... 終了
   NO  → 5へ
5. 意識: 簡単な指示に従えるか?
   NO  → I（赤） ... 終了
   YES → II（黄） ... 終了
```
- プロファイルは定数テーブルとして外部化し、将来 `US-START`（呼吸数 >30 のみ、CRT >2秒）等を追加可能にする。
  v1は `JP-FDMA` のみ実装し、設定画面には表示しない（内部構造だけ用意）。
- 採用基準値はリファレンス画面(S5)に明記する。

### 3.3 症例ジェネレータ仕様
**方式: 目標区分を先に決め、その区分になる値域から逆向きに生成する（Target-first generation）。**
ランダムに値を振ってから判定する方式は区分の出現比率が偏るため採用しない。

#### 生成手順
1. 目標区分 `target` と「確定ステップ」`decidingStep` を決める（10問連続モードは §2.4 の構成表に従う）。
2. `decidingStep` に至るまでの各項目は「通過する値域」から抽選、`decidingStep` の項目は「該当する値域」から抽選。
3. `decidingStep` より後の項目も**矛盾のない値を生成して表示する**（判定には不要だが、
   「不要な情報を無視できる」こと自体が訓練になる）。
4. 境界値バイアス: 設定値の確率（既定35%）で、`decidingStep` の値を境界値ピッタリにする。
5. **通過側の数値項目にも、同じ確率で独立に境界値バイアスをかける。**
   呼吸数 29 を通過させてから循環で確定する症例は難度が高く、教育価値が大きいため。

#### 値域テーブル
| 項目 | フィールド | 通過（正常）側 | 該当（異常）側 | 境界値 |
|---|---|---|---|---|
| 歩行 | `canWalk` | `false` | `true`(=III) | — |
| 自発呼吸 | `hasSpontaneousBreathing` | `true` | `false` | — |
| 気道確保後 | `breathingAfterAirway` | `true`(=I) | `false`(=0) | — |
| 呼吸数 | `respiratoryRate` | 10–29 | **4–9** または 30–44 | 9, 10, 29, 30 |
| 橈骨動脈 | `radialPulsePalpable` | `true` | `false` | — |
| 脈拍 | `pulseRate` | 60–119 | 120–160（または<50） | 119, 120 |
| CRT | `crtSeconds` | 1.0–1.9 | 2.0–4.0 | 1.9, 2.0 |
| 指示応答 | `obeysCommands` | `true` | `false` | — |
| 反応の種類 | `nonObeyingResponse` | `null` | 声のみ / 体動のみ / 無反応 | — |

> **実測モードでは呼吸数を判定閾値から 4 回以上離す（`rrMargin = 4`）。**
> 観察して数える方式では分解能が観察時間に縛られ、±1 の真の境界値を判別できない。
> 根拠と値域表は `docs/OBSERVATION.md` §2 を参照。
>
> | 帯 | 数値モード | 実測モード | 15秒観察時の呼吸回数 |
> |---|---|---|---|
> | 該当（下限） | 4–9 | **4–5** | 1.00–1.25 回 |
> | 通過 | 10–29 | **14–25** | 3.50–6.25 回 |
> | 該当（上限） | 30–44 | **34–44** | 8.50–11.00 回 |
>
> 歩行可能な症例（III類）の軽症域も通過域との交差を取る（14–20）。
> 歩行可能なら呼吸数は評価されないが、実測モードでは利用者が胸郭の動きを見てしまうため、
> **どの症例であれ閾値付近の曖昧な値を提示してはならない。**

> **呼吸数の下限域は 4–9 とする（当初案の 0–9 から変更）。**
> 呼吸数 0 は「自発呼吸あり」と矛盾するため、自発呼吸がある症例で生成してはならない。
> 呼吸数 0 は `hasSpontaneousBreathing === false` の症例でのみ使う。

#### 整合性制約（生成後に必ず満たすこと）
- `radialPulsePalpable === false` のとき `pulseRate` は表示しない（`null`）。触知できない＝数えられない。
- `pulseRate ≥ 120` のとき `crtSeconds` は 1.5以上に寄せる（生理学的整合）。ただし循環ステップを
  「通過」させる症例では `crtSeconds < 2.0` を厳守する（判定の一貫性が優先）。
- `canWalk === true`（III類）のとき、他のバイタルは軽症域（RR 12–20, 脈 70–100, CRT <2s, 指示応答可）で生成。
- `hasSpontaneousBreathing === false` のとき `respiratoryRate = 0`、`obeysCommands = false`。
- `obeysCommands === true` ⟺ `nonObeyingResponse === null`。従命できる症例に「反応の種類」は無い。
- **無呼吸の症例は `voiceOnly`（声のみ）にならない。** 呼吸が無いのに発声する症例は
  生理学的に矛盾する。`movementOnly` か `none` に限る。
- イラスト・状況テキストは `canWalk` と整合する集合からのみ選択。

#### 不変条件（テストで担保）
> 任意のシードで生成した症例に `judge()` を適用した結果は、必ず `target` と一致する。
> また `judge()` が返す `decidingStep` は、生成時に意図した `decidingStep` と一致する。

### 3.4 傷病者イラスト仕様
- 形式: インラインSVG（React コンポーネント）。ピクトグラム＋簡易陰影の抽象表現。血液表現は最小限。
- **全種が胸郭アニメーションの契約に従う**（`docs/OBSERVATION.md` §5）。
  胸郭を `class="chest"` のグループにまとめ、`animationDuration` に 1 呼吸周期の秒数を渡す。
  `transform-origin` は横隔膜位置。吸気40%:呼気60%の非対称波形。
  無呼吸の症例には `chest` クラスも `animationDuration` も付けない（**静止が手がかり**）。
- バリエーション（最低12種）:
  - 歩行可: 自力歩行、やや足を引きずって歩行、腕を押さえて歩行、肩を貸されず自立歩行、立って手を挙げる
  - 歩行不可: 座り込み、仰臥位、腹臥位、瓦礫に下肢を挟まれる、壁にもたれて動けない、車内に閉じ込め、立位だが動けない
- 各イラストに `canWalk` 属性と、対応する状況テキスト候補を複数紐づける。
  **状況文は生成時に1つ抽選して症例に固定する。** 再描画のたびに文が変われば、
  計測の途中で表示が入れ替わってしまう。

#### カタログの構造（`src/domain/illustrations.ts`）

| 項目 | 意味 |
|---|---|
| `id` | SVG の識別子。**複数のカタログ項目が同じ図を共有してよい** |
| `pose` | 姿勢の分類 |
| `situationKeys` | 状況文の翻訳キー候補（1件以上） |
| `canWalk` | 歩行可否 |

> **状況文キーはカタログ全体で一意である。** 状況文が歩行可否の決め手なので、
> 同じ文が2箇所に現れると、一つの文が「歩ける」と「歩けない」の両方を
> 意味し得てしまう。テストで強制する。

#### 絵だけでは歩行可否を決められない症例

SPEC §7 最上段のリスク（「イラストだけでは歩行可否が判断できず『画像当てクイズ』になる」）
への対策として、**同じ姿勢を歩行可・歩行不能の両方に置く**。

| 姿勢 | 歩行可 | 歩行不能 |
|---|---|---|
| 立位 | 自分で立ち上がり、手を挙げて自力で歩いてきた | 立っているが、足が動かず歩けない |
| 座位 | 自力で歩いて集合場所まで来て、その場に座り込んだ | 床に座っているが、足に力が入らず立てない |
| 壁にもたれる | 自力で歩いてきて、壁にもたれて休んでいる | 壁にもたれたまま動けない |

> **またがる姿勢は同一の SVG を共有する。** 似た絵を別々に描くと、
> 気づかぬうちに「うなだれていたら歩けない」といった偽の手がかりを作り込む。
> 同一オブジェクトを参照すればそれが起こり得ない。テストで強制する。
>
> 立位だけは例外とし、歩幅と腕の垂れ方という**意図した弱い手がかり**を残す。
>
> **紛らわしい項目は各バケツの 40% 以下に抑える。** これを超えると
> 「絵と状況文を照合する」習慣ではなく「絵を疑う」反射を教えてしまい、
> 引っかけ問題集になる。残りの大半では絵が手がかりとして機能していなければならない。

> **「支えられて歩いている」は採用しない。** 介助歩行を自力歩行に含めるかは
> 現場の運用で割れる。判定基準が割れる症例を訓練に混ぜてはならない。
> 判定文言は「自力で歩行できる」であり、**状況文がそれを満たすか否かを
> 一読で断定できる書き方に限る。**
>
> 同じ理由で**小児は出さない**。小児は JumpSTART 法で基準が異なり、§1.6 で
> v1 スコープ外としている。成人の姿勢・状況のみで多様性を作る。

#### 見た目の個体差

同じ姿勢でも毎回同じ人形に見えないよう、**体格（0.9 / 1.0 / 1.06）と
髪型（短髪 / 長め / なし）**を振る。

> **一目で髪と分かる形だけを置く。** 外傷トリアージの訓練で頭部に意味の読めない印が
> あると、包帯や頭部外傷といった所見として読まれかねない。
> **判定に関わらないものが所見に見えるのは、見た目が単調であることより悪い。**
>
> 頭部は顔の描かれていない丸なので、裏に薄い円を敷いても「少し大きい頭」にしか
> 見えない。**髪は頭部の上に重ね、生え際の線が出る形で描く。**
> まとめ髪やヘルメットのつばは、臥位では頭から離れた丸・棒に見えるため採らない。

> **ドメインには置かない。** `TriageCase` は判定に関わる事実だけを持つ設計であり、
> 見た目は判定に一切関わってはならない。ドメインの外（`components/patients/appearance.ts`）に
> 置くことが、その制約を構造で保証する。
>
> **症例IDから決める。** 同じ症例は何度描き直しても同じ姿で現れる。
> 乱数を描画時に引くと、計測の途中で別人に変わってしまう。
>
> 体格の拡縮は**人物だけ**に掛け、地面や瓦礫には掛けない。接地点を支点にするので
> 足が浮かない。情景に挟まれた図（車室など）は拡縮から外す。
> 上限が 1.06 なのは、立位の頭頂が接地点から 170px 上にあり、
> これを超えると viewBox からはみ出して頭が切れるため。
>
> **髪は頭頂側の半分に収める。** 頭部と胸郭の間隔は最小 3px しかなく、
> 反頭頂側（胸郭のある側）へ伸ばすと呼吸の可動域に食い込む。
> 毛束も頭部の下端より下へは垂らさない。幾何テストが頂点ごとに検査する。
>
> **見た目が歩行可否と相関しないことをテストで確かめる。** 相関があると、
> 利用者はフローではなく見た目で答えるようになる。
- `alt` / `aria-label` には**答えを漏らさない**記述を入れる（例: 「地面に横たわる傷病者のイラスト」は可、
  「歩行不能の傷病者」は不可）。

### 4.3 主要な型定義（案）
```ts
export type Category = 'I' | 'II' | 'III' | '0';

// 「自発呼吸の有無」は単独では判定を確定させない（呼吸がなければ必ず気道確保の結果で
// 確定する）ため、独立したステップとして持たない。I類と0類の区別は category が担う
export type DecidingStep =
  | 'walk' | 'airway'
  | 'respiratoryRate' | 'circulation' | 'consciousness';

export interface TriageCase {
  id: string;
  patient: { illustrationId: string; situationKey: string };  // 表示文字列は持たない
  canWalk: boolean;
  hasSpontaneousBreathing: boolean;
  breathingAfterAirway: boolean | null;   // 自発呼吸なしの症例のみ
  respiratoryRate: number | null;         // 回/分
  radialPulsePalpable: boolean;
  pulseRate: number | null;               // 触知不能時は null
  crtSeconds: number;
  obeysCommands: boolean;
  /** 従命できない症例の反応。`obeysCommands === true` のときは null */
  nonObeyingResponse: 'voiceOnly' | 'movementOnly' | 'none' | null;
}

// ドメイン層は表示文字列を持たない。文章化は表示層が t() で行う（I18N.md §5）
export interface RationaleItem {
  key: string;                            // 翻訳キー（例 'rationale.rrHigh'）
  params?: Record<string, string | number>;
}

export interface Judgement {
  category: Category;
  decidingStep: DecidingStep;
  rationale: RationaleItem[];
}

export function judge(c: TriageCase, p: RuleProfile): Judgement;

// 矛盾した症例は黙って誤った区分を返さず、即座に失敗させる。
// 教育アプリにおいて誤った判定を提示することは、クラッシュより有害である
export class InconsistentCaseError extends Error {}
```

## 5. UI / UX 方針

### 5.1 デザイン原則
- **ページ本体をスクロールさせない。** 現場トリアージは「症例を見て即断する」のが本質であり、
  判断材料を見るのにスクロールが要る時点で訓練として成立しない。
  ルートを `h-dvh` の行グリッドに固定し、ヘッダーと回答バーを常に画面内へ留める。
  可変行には `minmax(0,1fr)` を使う。これがないと内容量でグリッドが押し広げられ `overflow-hidden` が効かない。
- **レイアウトの切り替えは「使える高さ」で判断する。** 端末の向き（orientation）では不十分で、
  横持ちでも背の高い端末があり、ウィンドウ分割やブラウザのツールバーでも使える高さは変わる。
  症例ペインをサイズコンテナにし、コンテナクエリ `@container pane (max-height: 440px)` で
  縦積みと横並びを切り替える。ビューポートではなくペイン自身の寸法で評価されるため、
  実ブラウザと静的スナップショットで同じ結果になり検証できる。
- **余った高さは傷病者イラストに回す。** 端末ごとの余剰は呼吸アニメーションの視認性に使うのが
  最も価値が高い（実測モードで数えられるかに直結する）。
- **常時表示を減らす。** 言語切替・提示方式・免責・累計成績は設定シートへ集約し、
  出題画面の高さを判定材料のために空ける。
  ただし**計測器は判定材料そのものなので常時表示する**（§2.2）。
  CRT と脈拍は元からバイタル表の2セルを占めており、そのセルを計測器へ置き換えるため
  増える高さはわずかで、イラストは 390×680 で約 330px を保つ。
- **角を落とさない。** ボタン・パネル・囲み線はすべて直角とする。
  実装は `src/index.css` の `@theme` で `--radius-*` を 0 にしており、
  `rounded-*` ユーティリティを書いても角丸にならない。消し漏れを防ぎ、
  今後追加するコンポーネントにも自動で効かせるため、個々のクラス削除ではなく
  テーマ変数の上書きで実現している。
  傷病者イラストの角（胸郭・頭部・頸部）は人体の形状であり、この対象外。
- **判定に必要な情報だけを大きく。** 装飾より可読性。現場を想起させる彩度は抑え、トリアージ色（赤黄緑黒）だけを強い色として使う。
- ダークモード対応（夜間訓練・屋外での視認性）。
- アニメーションは最小限（10問モードの集中を妨げない）。

### 5.2 操作
- 回答: タップ / キーボード `1`=I, `2`=II, `3`=III, `0`=0類, `Enter`=次へ
- 誤タップ防止: 回答確定後、200ms は次アクションを受け付けない
- 片手操作前提。スワイプ操作は誤操作リスクが高いため採用しない

### 5.3 アクセシビリティ
- トリアージ区分は **色のみに依存しない**（色＋ローマ数字＋和文＋パターン）
- コントラスト比 WCAG AA（4.5:1）以上
- 全操作がキーボードで到達可能、フォーカスリング明示
- 症例情報は `<dl>` 構造でスクリーンリーダー読み上げ可能、イラストの `aria-label` は答えを漏らさない
- 結果画面の正誤は記号＋テキストで表現
- 言語切替時に `document.documentElement.lang` を更新し、スクリーンリーダーの読み上げ言語を追従させる
- **動きだけで情報を伝えない。** `prefers-reduced-motion: reduce` の場合、実測モードの呼吸数提示を
  自動的に数値へフォールバックし、フォールバックしたことを画面に表示する（`docs/OBSERVATION.md` §3.7）
- **フォーカスを必ず見えるようにする。** ブラウザ既定のリングは、暗い背景と彩度の高いボタン
  （赤・黄・緑）の双方で十分な明暗差を得られない。爪の押下対象のように背景も枠も持たない
  ボタンでは既定のリングがほぼ見えない。白のリングに暗いオフセットを重ねる（`src/index.css`）
- **タッチ目標は 24×24 以上**（WCAG 2.2 の 2.5.8）。主要な操作は 44px を確保する

### 5.4 アクセシビリティの検証方法

宣言だけでは守られないため、機械で検査できる形にしている。

| 対象 | 方法 | テスト |
|---|---|---|
| ARIA・役割・名前・見出し階層 | axe-core を jsdom 上で実行。全画面とシートを巡回 | `tests/a11y.spec.tsx` |
| コントラスト比 | **生成CSSからテーマ色を読み、WCAG の式で計算する。** 値を手で写すと実際とずれる | `tests/contrast.spec.ts` |
| キーボード到達性 | Tab を送り、有効なボタンすべてに到達でき、各要素が名前を持つことを確認 | `tests/a11y.spec.tsx` |
| 色のみに依存しない | 区分は色＋ローマ数字＋和文＋枠線パターンの4重符号化 | `tests/learnMode.spec.tsx` |
| 動きだけに依存しない | `prefers-reduced-motion` で数値へフォールバック | `tests/measure.spec.tsx` ほか |

> **コントラストの計算器自体もテストする。** 白黒が 21:1、同色が 1:1 になることを
> 確かめる項目を置いている。実際、最初の実装は線形 RGB とガンマ補正済み sRGB を
> 混ぜており、この自己検証がなければ誤った「合格」を出していた。
>
> axe-core はレイアウトを持たない jsdom ではコントラストと寸法を評価できない。
> 見逃しではなく、別手段で検証している。

## 7. リスクと対応
| リスク | 対応 |
|---|---|
| START法の基準値が組織により異なる（特に呼吸数の下限、循環指標） | 採用基準をリファレンスに明示。ルールプロファイルで外部化し差し替え可能に |
| イラストだけでは歩行可否が判断できず「画像当てクイズ」になる | 状況テキスト1行を必須添付。さらに**同じ姿勢を歩行可・歩行不能の両方に置き、両者で同一の SVG を共有する**（§3.4）。絵が答えを決めない構造にする |
| 紛らわしい症例が多すぎて引っかけクイズ化する | 紛らわしい項目を各バケツの 40% 以下に制限し、テストで強制（§3.4） |
| タイムの改ざん（DevTools等） | 自己申告SNS共有に限定。ランキング非実装を明言 |
| 医療行為の誤解 | 恒久的な免責表示。実臨床判断への適用を否定する文言 |
| 境界値ばかりで現場感を失う | 境界値出題率を設定可能に（既定35%）。残りは余裕のある値域から生成 |
| 実測モードで利用者が「数えられない」と感じて離脱する | 観察時間は無制限、タップ計数は回答の前提条件にしない。数えずに判断してよい |
| 実測モードのタイムを数値モードと比較してしまう | 自己ベストを提示方式ごとに分離。X ポスト文にもモードを明記 |
| アニメーションの周期がずれ、誤った呼吸数を教える | CSS の `animation-duration` で駆動（コンポジタ駆動）。`周期 × 呼吸数 === 60` をテストで保証 |
| X Web Intent の仕様変更 | `share.ts` に隔離。Web Share API へのフォールバックを用意 |
| 英語UIの利用者が米国版STARTの基準で採点されていると誤解し、誤った基準を習得する | **言語と `RuleProfile` を完全に独立させる。**英語UIでも採用基準が `JP-FDMA` であることを免責とS5に常時表示（I18N.md §2） |

## 8. 決定事項 / 未確定事項

   Xポスト文の `url` パラメータ(§2.5)とOGPの `og:url` にこれを使用する。

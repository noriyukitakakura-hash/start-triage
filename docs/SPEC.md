## 1. 企画

### 1.1 背景と課題
災害現場・多数傷病者事案における一次トリアージ（START法）は、
**「判定の順序」と「境界値の即断」** が成否を分ける。しかし実際の訓練機会は年数回に限られ、
紙のフローチャートを「読んで理解する」ことと「30秒以内に判定し続けられる」ことの間には大きな差がある。

### 1.2 プロダクト概要
ブラウザで動く、START法の反復トレーニングアプリ。
1症例ごとに「傷病者のイラスト（歩行可否の手がかり）」と「ランダム生成されたバイタル」を提示し、
利用者が4つのトリアージ区分から選択する。学習モードで理屈を固め、10問連続モードで速度と正確性を測る。

### 1.3 ターゲット
- 消防職員・救急隊員（救命士含む）
- DMAT隊員、災害拠点病院の医師・看護師
- 看護学生・医学生・救急救命士養成課程
- 事業所/自治体の防災訓練参加者（一般向け導入）

### 1.4 提供価値 / 差別化
| 観点 | 本アプリ |
|---|---|
| 判定の体得 | 境界値（呼吸9/10回、29/30回、脈拍120、CRT 2秒）を意図的に高頻度出題し、迷いを潰す |
| 速度の可視化 | 10問連続の経過時間を計測。自己ベストを更新する動機づけ |
| 外部発信 | 10問全問正解時のみ、Xへタイムを投稿可能（達成の希少性＝投稿価値） |
| 導入障壁 | インストール不要・ログイン不要・完全無料・オフライン動作 |

### 1.5 KPI（初期）
- 1セッションあたりの平均出題数 ≥ 20問
- 10問連続モードの全問正解率（初回 vs 5回目以降）の改善
- Xポスト実行数 / 全問正解数

### 1.6 スコープ外（v1）
- ログイン、サーバー保存、全国ランキング（※時間はクライアント計測のため検証不能。1.7参照）
- 二次トリアージ（PAT法）、小児用START（JumpSTART）
- マルチプレイ（3言語目以降の多言語化も非スコープ。ja/en は対応する → `docs/I18N.md`）

### 1.7 医療・倫理・法務上の注意（必須記載事項）
- アプリ内に恒久表示する免責: **「本アプリは教育・訓練目的のシミュレーションです。実際の傷病者対応は所属機関のプロトコル・指示に従ってください。」**
- START法の基準値は地域・組織のプロトコルにより差異がある。採用基準を明示し、プロファイル切替可能な設計とする（§3.2）。
- 傷病者イラストは**実写を使用しない**。実在人物の負傷画像は権利・倫理・心理的配慮の観点で不適。自前のベクターイラストで表現する。
- 経過時間はクライアント計測であり改ざん可能。**SNSへの自己申告共有に限定し、競争ランキングは実装しない**（将来実装する場合はサーバー側での出題・計測検証が前提）。

## 2. 機能仕様

### 2.1 画面一覧
| ID | 画面 | 概要 |
|---|---|---|
| S1 | ホーム | モード選択、自己ベストタイム、学習統計サマリ、リファレンスへの導線 |
| S2 | 学習モード | 1症例ずつ出題 → 回答 → 即時フィードバック＋解説 → 次へ（無制限） |
| S3 | 10問連続モード | 経過タイマー表示、進捗(n/10)、フィードバックなしで連続出題 |
| S4 | 結果 | 10問の正誤一覧、タイム、全問正解時のみXポストボタン、再挑戦 |
| S5 | リファレンス | START法フローチャート、4区分の定義、採用基準値の明示 |
| S6 | 設定 | ルールプロファイル、境界値出題頻度、サドンデス有無、タイマー表示、統計リセット |

### 2.2 症例の提示内容（1症例カード）
```
┌─────────────────────────────┐
│  [傷病者イラスト]                  │  ← 歩行可否の手がかり
│  「呼びかけに応じて自力で歩いてきた」      │  ← 状況テキスト1行（曖昧性排除）
├─────────────────────────────┤
│ 呼吸      32 回/分                 │
│ 橈骨動脈   触知可                   │
│ 脈拍      110 回/分                │
│ CRT       1 秒未満                  │
│ 指示応答   従える                   │
└─────────────────────────────┘
│ [ I 赤 ] [ II 黄 ] [ III 緑 ] [ 0 黒 ] │
```
- **歩行可否は画像で判断**。ただし「立っている＝歩行可能」とは限らないため、画像に加えて
  状況テキスト1行を必ず添え、判断の曖昧性を排除する（例: 立位イラスト＋「立っているが足が動かず歩けない」）。
- **自発呼吸なしの症例のみ**、回答前に `気道確保を行う` ボタンを1回挟む。
  押すと「気道確保後も自発呼吸なし」/「気道確保により呼吸再開（RR 14回/分）」が開示される。
  → これがないと I類（赤）と 0類（黒）の区別がテキスト読解になり、手技の順序が学習できない。
- 回答ボタンは **色・ローマ数字・和文ラベルの3重符号化**（色覚多様性への配慮、§5.3）。

### 2.3 学習モード (S2)
- 回答後に即時フィードバック: 正誤、正解区分、**判定が確定したステップのフローチャート上ハイライト**、解説文。
  - 解説文は生成した症例データから自動組み立て（例: 「歩行不能、呼吸数32回/分（30回以上）→ この時点で I類（赤）が確定。以降の評価は不要です。」）
- 「次の症例」で即次へ。回数無制限。中断・再開自由。
- セッション統計（出題数、正答率、区分別の誤答マトリクス）をlocalStorageに累積。

### 2.4 10問連続モード (S3/S4)
- 開始トリガー: ホームの「10問チャレンジ」→ カウントダウン3秒 → 1問目表示と同時にタイマー開始。
- 計測: `performance.now()` 差分。1問目描画完了から10問目回答確定まで。ミリ秒精度、表示は `M分SS.SS秒`。
- 出題中はフィードバックを一切出さない（正誤を伏せる）。
- 出題構成（固定比率＋シャッフル）:

| 正解区分 | 問数 |
|---|---|
| I類（赤） | 4 |
| II類（黄） | 2 |
| III類（緑） | 2 |
| 0類（黒） | 1 |
| ランダム | 1 |

  うち **4問以上を境界値症例**とする（下記 §3.3）。

  > **境界値の下限には構造的制約がある。** 境界値を取り得るのは呼吸数・循環・意識の
  > 3ステップのみで、III類（歩行）と0類（気道確保）は真偽値判定のため境界値が存在しない。
  > したがって下限を満たせるのは I類4問 + II類2問 = 6問のみであり、
  > 不足時は **I類・II類側の確定ステップを境界値可能なものへ差し替える**（区分の構成比は維持する）。
  > I類4問すべてが気道確保を引くと上限3問となり下限に届かないため、この差し替えが必須である。
- 結果画面: 10問の正誤一覧（各問の症例サマリと正解＋解説リンク）、合計タイム、自己ベスト更新表示。
- **10/10 の場合のみ** `Xに投稿する` ボタンを表示。9/10以下では非表示（文言: 「全問正解で投稿できます」）。
- サドンデス設定（既定OFF）: ONの場合、1問誤答した時点で即結果画面へ。

### 2.5 Xポスト仕様
- 方式: **X Web Intent**（APIキー・OAuth・サーバー不要）
  `https://x.com/intent/post?text=<encoded>&url=<appUrl>&hashtags=<tags>`
  を `window.open(url, '_blank', 'noopener,noreferrer')` で開く。
- 投稿URLには `?lang=<locale>` を付与し、投稿を見た人が投稿者と同じ言語で開けるようにする（I18N.md §7）。
- 投稿文テンプレート（編集可能な状態でXの作成画面に渡る。言語別に用意）:
  ```
  START法トリアージ 10問チャレンジ 全問正解！
  タイム 1分23.45秒
  #STARTトリアージ #災害医療 #トリアージ訓練
  ```
- 自己ベスト更新時は1行追加（`自己ベスト更新 🎉`）。
- 投稿ボタン押下をlocalStorageに記録（KPI計測用、送信はしない）。
- OGP: `index.html` に `og:title` / `og:description` / `og:image`（1200×630の静的PNG）を設定し、
  シェア時にカード表示されるようにする。

## 3. トリアージ判定ロジック（コアドメイン）

### 3.1 区分
| コード | 区分 | 色 | 意味 |
|---|---|---|---|
| `I` | I類・緊急治療群 | 赤 | 生命を救うため直ちに処置が必要 |
| `II` | II類・非緊急治療群 | 黄 | 多少の遅れが許容される |
| `III` | III類・軽処置群 | 緑 | 軽傷、歩行可能 |
| `0` | 0類・死亡群 | 黒 | 気道確保後も自発呼吸なし |

### 3.2 判定アルゴリズム（ルールプロファイル `JP-FDMA`、v1で実装）
```
1. 歩行可能か?
   YES → III（緑）  ... 終了
   NO  → 2へ
2. 自発呼吸はあるか?
   NO  → 気道確保
         → 呼吸再開 → I（赤） ... 終了
         → 再開せず → 0（黒） ... 終了
   YES → 3へ
3. 呼吸数 ≦ 9 または ≧ 30 回/分?
   YES → I（赤） ... 終了
   NO  → 4へ
4. 循環: CRT ≧ 2秒 または 橈骨動脈 触知不能?
   YES → I（赤） ... 終了
   NO  → 5へ
5. 意識: 簡単な指示に従えるか?
   NO  → I（赤） ... 終了
   YES → II（黄） ... 終了
```
- プロファイルは定数テーブルとして外部化し、将来 `US-START`（呼吸数 >30 のみ、CRT >2秒）等を追加可能にする。
  v1は `JP-FDMA` のみ実装し、設定画面には表示しない（内部構造だけ用意）。
- 採用基準値はリファレンス画面(S5)に明記する。

### 3.3 症例ジェネレータ仕様
**方式: 目標区分を先に決め、その区分になる値域から逆向きに生成する（Target-first generation）。**
ランダムに値を振ってから判定する方式は区分の出現比率が偏るため採用しない。

#### 生成手順
1. 目標区分 `target` と「確定ステップ」`decidingStep` を決める（10問連続モードは §2.4 の構成表に従う）。
2. `decidingStep` に至るまでの各項目は「通過する値域」から抽選、`decidingStep` の項目は「該当する値域」から抽選。
3. `decidingStep` より後の項目も**矛盾のない値を生成して表示する**（判定には不要だが、
   「不要な情報を無視できる」こと自体が訓練になる）。
4. 境界値バイアス: 設定値の確率（既定35%）で、`decidingStep` の値を境界値ピッタリにする。
5. **通過側の数値項目にも、同じ確率で独立に境界値バイアスをかける。**
   呼吸数 29 を通過させてから循環で確定する症例は難度が高く、教育価値が大きいため。

#### 値域テーブル
| 項目 | フィールド | 通過（正常）側 | 該当（異常）側 | 境界値 |
|---|---|---|---|---|
| 歩行 | `canWalk` | `false` | `true`(=III) | — |
| 自発呼吸 | `hasSpontaneousBreathing` | `true` | `false` | — |
| 気道確保後 | `breathingAfterAirway` | `true`(=I) | `false`(=0) | — |
| 呼吸数 | `respiratoryRate` | 10–29 | **4–9** または 30–44 | 9, 10, 29, 30 |
| 橈骨動脈 | `radialPulsePalpable` | `true` | `false` | — |
| 脈拍 | `pulseRate` | 60–119 | 120–160（または<50） | 119, 120 |
| CRT | `crtSeconds` | 1.0–1.9 | 2.0–4.0 | 1.9, 2.0 |
| 指示応答 | `obeysCommands` | `true` | `false` | — |

> **呼吸数の下限域は 4–9 とする（当初案の 0–9 から変更）。**
> 呼吸数 0 は「自発呼吸あり」と矛盾するため、自発呼吸がある症例で生成してはならない。
> 呼吸数 0 は `hasSpontaneousBreathing === false` の症例でのみ使う。

#### 整合性制約（生成後に必ず満たすこと）
- `radialPulsePalpable === false` のとき `pulseRate` は表示しない（`null`）。触知できない＝数えられない。
- `pulseRate ≥ 120` のとき `crtSeconds` は 1.5以上に寄せる（生理学的整合）。ただし循環ステップを
  「通過」させる症例では `crtSeconds < 2.0` を厳守する（判定の一貫性が優先）。
- `canWalk === true`（III類）のとき、他のバイタルは軽症域（RR 12–20, 脈 70–100, CRT <2s, 指示応答可）で生成。
- `hasSpontaneousBreathing === false` のとき `respiratoryRate = 0`、`obeysCommands = false`。
- イラスト・状況テキストは `canWalk` と整合する集合からのみ選択。

#### 不変条件（テストで担保）
> 任意のシードで生成した症例に `judge()` を適用した結果は、必ず `target` と一致する。
> また `judge()` が返す `decidingStep` は、生成時に意図した `decidingStep` と一致する。

### 3.4 傷病者イラスト仕様
- 形式: インラインSVG（React コンポーネント）。ピクトグラム＋簡易陰影の抽象表現。血液表現は最小限。
- バリエーション（最低12種）:
  - 歩行可: 自力歩行、やや足を引きずって歩行、腕を押さえて歩行、肩を貸されず自立歩行、立って手を挙げる
  - 歩行不可: 座り込み、仰臥位、腹臥位、瓦礫に下肢を挟まれる、壁にもたれて動けない、車内に閉じ込め、立位だが動けない
- 各イラストに `canWalk` 属性と、対応する状況テキスト候補を複数紐づける。
- `alt` / `aria-label` には**答えを漏らさない**記述を入れる（例: 「地面に横たわる傷病者のイラスト」は可、
  「歩行不能の傷病者」は不可）。

## 4. 技術仕様

### 4.1 技術スタック
| 領域 | 選定 | 理由 |
|---|---|---|
| ビルド | Vite 7 | 高速、静的SPA出力 |
| 言語 | TypeScript (strict) | ドメインモデルの型安全性 |
| UI | React 19 | 実績・エコシステム |
| スタイル | Tailwind CSS v4 | 小規模・高速な実装 |
| 状態 | `useReducer` + Context | サーバー状態なし、規模が小さいためライブラリ不要 |
| i18n | 自前の軽量実装（ja/en 切替） | バンドル約40KB削減と型安全性のため i18next を採用しない → `docs/I18N.md` §3 |
| テスト | Vitest + React Testing Library | ロジックの境界値テストが主目的 |
| PWA | vite-plugin-pwa | 訓練会場での不安定な回線に備えオフライン動作 |
| 配信 | Cloudflare Pages | 完全静的、転送量無制限で無料、TLS自動。詳細は `docs/INFRA.md` |
| CI | GitHub Actions | typecheck / lint / test / build |

**バックエンドなし。** 永続化はすべて localStorage。これによりホスティング費ゼロ、個人情報の取得ゼロ。

### 4.3 主要な型定義（案）
```ts
export type Category = 'I' | 'II' | 'III' | '0';

// 「自発呼吸の有無」は単独では判定を確定させない（呼吸がなければ必ず気道確保の結果で
// 確定する）ため、独立したステップとして持たない。I類と0類の区別は category が担う
export type DecidingStep =
  | 'walk' | 'airway'
  | 'respiratoryRate' | 'circulation' | 'consciousness';

export interface TriageCase {
  id: string;
  patient: { illustrationId: string; situationKey: string };  // 表示文字列は持たない
  canWalk: boolean;
  hasSpontaneousBreathing: boolean;
  breathingAfterAirway: boolean | null;   // 自発呼吸なしの症例のみ
  respiratoryRate: number | null;         // 回/分
  radialPulsePalpable: boolean;
  pulseRate: number | null;               // 触知不能時は null
  crtSeconds: number;
  obeysCommands: boolean;
}

// ドメイン層は表示文字列を持たない。文章化は表示層が t() で行う（I18N.md §5）
export interface RationaleItem {
  key: string;                            // 翻訳キー（例 'rationale.rrHigh'）
  params?: Record<string, string | number>;
}

export interface Judgement {
  category: Category;
  decidingStep: DecidingStep;
  rationale: RationaleItem[];
}

export function judge(c: TriageCase, p: RuleProfile): Judgement;

// 矛盾した症例は黙って誤った区分を返さず、即座に失敗させる。
// 教育アプリにおいて誤った判定を提示することは、クラッシュより有害である
export class InconsistentCaseError extends Error {}
```

### 4.4 localStorage スキーマ
```ts
// key: "triage-start:v1"
{
  schemaVersion: 1,
  bestTimeMs: number | null,
  challengeHistory: Array<{ at: string; correct: number; timeMs: number; posted: boolean }>, // 直近50件
  learnStats: { total: number; correct: number; confusion: Record<Category, Record<Category, number>> },
  settings: { locale: 'ja' | 'en'; profile: 'JP-FDMA'; boundaryRate: number; suddenDeath: boolean; showTimer: boolean }
  // locale と profile は独立。言語切替で判定基準を変えてはならない（I18N.md §2）
}
```
`schemaVersion` 不一致時はマイグレーションまたは破棄（破棄時は確認ダイアログなしで初期化、ただし次回起動時に通知）。

## 5. UI / UX 方針

### 5.1 デザイン原則
- **判定に必要な情報だけを大きく。** 装飾より可読性。現場を想起させる彩度は抑え、トリアージ色（赤黄緑黒）だけを強い色として使う。
- ダークモード対応（夜間訓練・屋外での視認性）。
- アニメーションは最小限（10問モードの集中を妨げない）。

### 5.2 操作
- 回答: タップ / キーボード `1`=I, `2`=II, `3`=III, `0`=0類, `Enter`=次へ
- 誤タップ防止: 回答確定後、200ms は次アクションを受け付けない
- 片手操作前提。スワイプ操作は誤操作リスクが高いため採用しない

### 5.3 アクセシビリティ
- トリアージ区分は **色のみに依存しない**（色＋ローマ数字＋和文＋パターン）
- コントラスト比 WCAG AA（4.5:1）以上
- 全操作がキーボードで到達可能、フォーカスリング明示
- 症例情報は `<dl>` 構造でスクリーンリーダー読み上げ可能、イラストの `aria-label` は答えを漏らさない
- 結果画面の正誤は記号＋テキストで表現
- 言語切替時に `document.documentElement.lang` を更新し、スクリーンリーダーの読み上げ言語を追従させる

## 7. リスクと対応
| リスク | 対応 |
|---|---|
| START法の基準値が組織により異なる（特に呼吸数の下限、循環指標） | 採用基準をリファレンスに明示。ルールプロファイルで外部化し差し替え可能に |
| イラストだけでは歩行可否が判断できず「画像当てクイズ」になる | 状況テキスト1行を必須添付。ユーザーテストで曖昧な組み合わせを除去 |
| タイムの改ざん（DevTools等） | 自己申告SNS共有に限定。ランキング非実装を明言 |
| 医療行為の誤解 | 恒久的な免責表示。実臨床判断への適用を否定する文言 |
| 境界値ばかりで現場感を失う | 境界値出題率を設定可能に（既定35%）。残りは余裕のある値域から生成 |
| X Web Intent の仕様変更 | `share.ts` に隔離。Web Share API へのフォールバックを用意 |
| 英語UIの利用者が米国版STARTの基準で採点されていると誤解し、誤った基準を習得する | **言語と `RuleProfile` を完全に独立させる。**英語UIでも採用基準が `JP-FDMA` であることを免責とS5に常時表示（I18N.md §2） |
